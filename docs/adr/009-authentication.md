# ADR-009: Authentication with Better Auth

## Status
Accepted

## Date
2026-11-02

## Context

PRD open question 7: Better Auth or Auth.js. Milestone 1 needs email and password sign-up, email verification, password reset, database sessions that can be revoked, a per-tenant idle timeout that only real activity extends, an absolute session lifetime, "sign out everywhere", and optional TOTP 2FA that a tenant can require (FR-ONB-1, FR-ONB-7, FR-USR-2, FR-USR-3). Login, reset, verification and invites need rate limits (FR-USR-4).

The old web app used Auth.js with JWT sessions. Its email and password provider only works with JWT sessions, so sessions couldn't be revoked, and the idle timeout needed a timestamp carried inside the token plus client-side activity calls to update it.

Checked on 2026-11-02:

- **Auth.js v5** has never had a stable release: it is still `5.0.0-beta.32`, the version the old app runs. Its email and password provider still requires JWT sessions.
- **Better Auth 1.7.15** is MIT-licensed, stable since 2024 and actively released, with a Drizzle adapter. Its telemetry is off unless enabled.

A spike ran Better Auth 1.7.15 against PostgreSQL 18 as `comprobify_erp_app`:

| Check | Result |
|---|---|
| IDs generated by the database with `uuidv7()` | Works with `generateId: false` |
| Sign-in refused until the email is verified | Works |
| Verification consumed by a server call, not by the emailed link | Works |
| Database session read from the cookie | Works |
| Reading the session doesn't extend it | Works with `disableSessionRefresh` |
| An extra session field we update ourselves | Works |
| Revoke all sessions | Works, but deletes rows from `sessions` |
| Password reset token is single-use | Works, but deletes expired rows from `verifications` |
| TOTP: enable, verify, and sign-in asks for the second factor with no session issued first | Works |
| Built-in rate limit | Applies over HTTP only, not to direct server calls |

## Decision

**Better Auth for credentials, sessions and TOTP.** Email and password, database sessions and the `twoFactor` plugin. Not its `organization` plugin: tenants, twins, memberships and roles are ours, because they need RLS, the `twin_of` link and mirrored memberships (PRD 7.4).

**Its tables are global identity tables:** `users`, `sessions`, `accounts`, `verifications`, and `two_factors` when 2FA arrives. Our `rate_limit_hits` sits beside them. None has a `tenant_id`, so RLS doesn't apply to them. Everything tenant-owned, including memberships and the audit log, lives in our own tables with RLS.

**Better Auth gets its own Drizzle instance on the app role's pool.** This is the one exception to "all data access goes through `withTenant` or `withSystem`" (NFR-SEC-2). It's limited to the tables above, and the rate limiter uses it too. Any tenant table it touched by mistake would raise, because it never sets a context.

**`DELETE` on `sessions`, `verifications` and `rate_limit_hits` only, plus `two_factors` when 2FA arrives.** These rows are credentials and counters, not business records. Sign-out, revocation, used tokens, old rate-limit hits and turning 2FA off delete them. Application tables keep no `DELETE`, and an integration test checks the exact list.

**Rules we implement around it:**

- **Email verification:** links point to our page. `GET` only checks the token; the page's `POST` consumes it through Better Auth's server API (Appendix B, lesson 5). Its own `GET /verify-email` route is never linked.
- **Idle timeout:** session refresh is off. We keep `last_activity_at` on the session, updated only by an explicit activity call from real input, never by page loads or polling. The timeout is per tenant, with an absolute lifetime on top (FR-USR-2).
- **Active tenant:** the session stores the active tenant. The switcher changes it after checking membership in core.
- **2FA required by a tenant:** checked by us when the session enters that tenant.
- **Rate limits:** our own, stored in Postgres, one per abuse vector: login, password reset, verification and invites (Appendix B, lesson 15). Better Auth's limiter only sees HTTP, and our forms call it from server actions, so no Better Auth route is mounted at all. Keys are hashed. Failed sign-ins count against the email and the address; a successful one doesn't. The address is the last `x-forwarded-for` entry, which Caddy adds. A loopback address means no proxy, as in local development, where only the per-email limits apply.
- **Duplicate sign-up:** Better Auth answers it like a new sign-up and creates, sends and changes nothing, so the form can't reveal which emails have accounts. The old app showed "email taken"; this is deliberately stricter.
- **Verification and reset emails:** Better Auth writes their tokens outside any transaction of ours, so they are enqueued after its write, the one exception to transactional enqueue. If one is lost, the user asks for another.
- **Super admin:** a flag on `users`, set by an operator script, never by sign-up.

**Where it lives:** `packages/core/src/identity` builds the Better Auth instance from injected config, so core stays framework-free. The web app adds the Next.js cookie plugin and the route handler.

**The same library is planned to be the OAuth 2.1 authorization server for MCP** (PRD 5.14, Milestone 11+), through `@better-auth/oauth-provider` and `@better-auth/mcp`, released alongside Better Auth. Their 1.7.15 source covers what the MCP authorization spec requires: PKCE with S256 only, authorization server metadata (RFC 8414), dynamic client registration (RFC 7591), protected resource metadata in `WWW-Authenticate` challenges (RFC 9728), audience-bound tokens through `resource` (RFC 8707), refresh tokens, revocation, introspection, a consent page we own, and JWT access tokens with JWKS. Not yet run end to end: Milestone 11 starts with a spike. One design rule carries over from now: a token acts for exactly one tenant, chosen on the consent page, so tenancy stays ours rather than in the library.

## Consequences

### Positive
- Sessions can be revoked one at a time or all at once, and the idle timeout is a column, not a token workaround.
- Password hashing, token handling and TOTP come from a maintained library rather than our own code.
- Users, sessions and the switcher fit the twin model without fighting an organization plugin.
- One library covers user login now and the MCP authorization server later.

### Negative
- One documented exception to the data-access rule, and `DELETE` on three tables.
- Better Auth's schema is generated, then adapted to our conventions (uuid keys). Upgrades need that check repeated.
- We still own rate limiting, the verification page and the idle timeout.

## Alternatives considered

- **Auth.js v5**: still in beta, and email and password forces JWT sessions, which is what the old app had to work around. It is a client library, with no OAuth authorization server for MCP.
- **Our own implementation**: full control, but we'd own password hashing, token rotation, TOTP and their security reviews.
- **Better Auth's `organization` plugin**: doesn't model the test twin, mirrored memberships or RLS-backed tenancy.
